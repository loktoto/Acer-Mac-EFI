Acer hackintosh — system-level Touch ID recon findings (2026-11-27, read-only)
==============================================================================

All observations came from static analysis; no system file, NVRAM setting or
authorization rule was changed during this recon.

  /System/Library/Frameworks/LocalAuthentication.framework/Support/coreauthd

  RemoteServiceDiscovery (dyld shared cache, x86_64h)

Disassembly saved alongside this file:

Platform gate
-------------
  BiometricKit:_isTouchIDPlatform
    -> _isTouchIDPlatformWithFailure
       - remote_device_copy_unique_of_type(3); wait for connected callback
       - remote_device_copy_unique_of_type(2); if found, cached result = true
       - otherwise log "isTouchIDPlatform(): No remote device!" and result = false
  It does NOT inspect the board-id or SMBIOS model. On this machine no remote
  device exists (no SEP IOKit node), so the gate fails.

Remote-device transport
-----------------------
  biometrickitd imports only:
    remote_device_copy_unique_of_type, remote_device_copy_service,
    remote_device_get_state
  It does NOT import remote_device_authenticate.
  No crypto/attestation imports at all: no SecKey*, SecTrust*, SecCertificate*,
  CommonCrypto, ECDH, HMAC, or signature-verification functions.

  -[BiometricKitBridgeTransport setupConnection]:
    remote_device_copy_unique_of_type -> remote_device_get_state ->
    enumerate service names (UTF8String) -> remote_device_copy_service ->
    -[BridgeXPCConnection initForRemoteService:] -> activateConnection:

  Service names observed: com.apple.BiometricKitBridge.executive,
                          com.apple.BiometricKitBridge.transport

  BridgeXPC imports:
    remote_service_create_connected_socket, socketpair,
    xpc_dictionary_*, xpc_array_*, xpc_data_*, NSJSONSerialization,
    NSPropertyListSerialization.
  No crypto imports. Transport appears to be XPC objects over a socket.

Envelope format (from -[BiometricKitBridgeTransport handleEnvelope:])
---------------------------------------------------------------------
  Incoming value is an NSArray of exactly 4 elements:
    [0] NSNumber    protocol version (assert: protocolVersion == PROTOCOL_VERSION)
    [1] NSNumber    message/reply flag
    [2] NSString    reply ID (a UUID string generated by the sender)
    [3] NSObject    payload (dictionary/array; looked up with objectForKeyedSubscript:)
  Replies reuse the same 4-slot shape; sendMessage:andWaitForReply: matches the
  reply by reply ID. -performCommand:input:output:capacity: expects reply[1] to be
  NSData or BTNil.

  Gap: the numeric command IDs are dispatched through a selector table in the
  binary's data section; static extraction of the full table is still pending.

Daemon-side bridge methods (ObjC interface BiometricKitBridgeConnection)
------------------------------------------------------------------------
  checkBridgeConnection, getBridgeVersion:, setBridgeClientVersion:,
  getServiceOpened:, getSystemBootTime:, getMachTimebaseInfo:, getOSVersion:,
  performCommand:input:output:capacity:, calibrationDataFromEEPROM,
  calibrationDataFromFDR, serviceStatuswithDatacontinueTimeDelta:

coreauthd — the hard part
-------------------------
  Imports:
    LACDTORatchetSEPInterface, LACDTORatchetSEPStateParser,
    LACDTOSensorTrustService, LACKeyBagProvider,
    SecAccessControlCreateWithFlags / GetConstraints / CopyData,
    MKBGetDeviceLockState
  Strings: bootstrapSEP, sensorTrust, Touch ID button monitoring,
    LACPolicyLocationBasedDeviceOwnerAuthenticationWithBiometricRatchet
  Own classes: DTORatchetHandler, DTOService. 31 ratchet-related references.

  Touch ID unlock therefore requires SEP-backed ratchet, sensor trust and
  keybag operations, not only a successful sensor match.

Verdict
-------
  * Faking the bridge device is not blocked by host-side attestation: this is
    the encouraging half.
  * Implementing all bridge commands needs either a reference Touch ID Mac to
    capture traffic, or a long static-RE exercise over the selector/command
    tables, followed by live iteration with SIP disabled.
  * coreauthd is the wall: its SEP ratchet / sensor-trust / keybag path would
    have to be patched or bypassed as well (Mach-O patching or dyld-cache
    surgery), with SIP and authenticated-root off permanently.
  * There is no known debug/environment hook to inject a fake remote device.
  * A working prototype therefore requires a SIP-off reboot performed by the
    user (Recovery/NVRAM on this hackintosh), which ends the current session.

Addendum 2026-11-27 01:18
-------------------------
Live harness (research/fake-bridge-probe/) can run a COPY of biometrickitd as
an unprivileged user with an injected dylib; SIP and launchd are untouched.

  isTouchIDPlatform -> interposed true
  setupConnection -> no-op
  sendMessage:andWaitForReply: -> logs and fabricates replies

Observed on the wire:
  - handshake message @[@2] expects a 2-element reply (getBridgeVersion shape)
  - command messages are 4-element arrays: [3, 0, NSData, capacity]
  - bridge command NSData header: "BM" + uint16 command + uint32 version 1
    (e.g. 42 4d 01 00 01 00 00 00 = command 1).
  - a 12-byte variant was observed: 42 4d 01 00 01 00 00 00 03 00 00 00,
    with capacity 4, i.e. a 4-byte input value after the 8-byte header.
  - commands 1..0x60 were invoked live through
    -[BiometricKitXPCServerMesa performCommand:inValue:inData:inSize:outData:outSize:]
    (outData is a buffer pointer; outSize is a capacity-in/size-out pointer).

The fake replies currently use dummy data; the daemon accepts the status but
does not expose an enrolled identity. No Touch ID UI state was reached.

Addendum 2 (2026-11-27 01:25)
------------------------------
Command -> expected reply length table was extracted from disassembly and fed
to the fake bridge (0x01=4, 0x30=1, 0x22=0x11, ...). getCommProtocolVersion
now succeeds live (CMD 1 -> outSize=4, value 03 00 00 00).

Enrollment state:
  - getEnrollmentCount is a one-instruction read of ivar _enrollmentCount
    (type q / int64, offset 416) on BiometricKitXPCServerMesa.
  - The dylib can locate and write that ivar, but the copied daemon never
    reaches its run loop while setupConnection/sendMessage are intercepted,
    so a delayed write never fires. Writing the ivar before init is undone
    by daemon startup.
  - Payload bytes for identity/catacomb commands are still unknown; a fake
    bridge with only correct lengths and zero payload does not produce an
    enrolled identity.

Conclusion: this is the end of what can be learned without either a real
Touch ID Mac to capture traffic, or SIP disabled to run the real daemon with
the injected dylib.

Addendum 3 (2026-11-27 01:42)
------------------------------
LAContext baseline on this machine:
  canEvaluatePolicy(.deviceOwnerAuthenticationWithBiometrics) = false
  error = com.apple.LocalAuthentication code=-6 "Biometry is not available."
  biometryType = 0

LocalAuthenticationCore (cached framework) imports:
  AppleKeyStore (AKSEventsRegister/Unregister), MobileKeyBag, Security,
  IOKit, NSXPCConnection/Interface/Listener. It does NOT import BiometricKit.
AppleKeyStore imports raw XPC mach-service APIs (xpc_connection_create_mach_service,
send_message_with_reply_sync) and no biometry-specific symbols.

Conclusion: registering a user-domain com.apple.biometrickitd would not change
LAContext's answer, because the availability decision also goes through
AppleKeyStore / MobileKeyBag / SEP. This route is a dead end without SEP.

Addendum 4 (2026-11-27 19:25)
------------------------------
Fresh trace of the lock-screen Touch ID icon decision:

  loginwindow.app contains NO Touch ID / fingerprint image asset at all;
  the icon is not a swappable loginwindow resource.

  coreauthd contains the gate:
    -[LAFUSConfirmation _startMonitoringTouchIDButton]
    -[LAFUSConfirmation _touchIDButtonPressed]
    +[DaemonUtils deviceHasTouchIDAndSecureDoublePress]
  and an entitlement-gated XPC listener APTouchIdModuleListener
  (required entitlement: com.apple.LocalAuthentication.aptouchid).
  Another private entitlement observed: com.apple.private.CoreAuthentication.SPI.

  deviceHasTouchIDAndSecureDoublePress eventually calls
    +[LACMobileGestalt deviceHasTouchID]  (LocalAuthenticationCore, dyld cache)
  which does:
    MGIsQuestionValid(question) then MGGetBoolAnswer(question)
  and caches the BOOL in _deviceHasTouchID.hasTouchID.
  FaceID / OpticID use the identical pattern.

  Built research/gestalt-probe (ObjC, dlopen LocalAuthenticationCore) and
  called the same class methods in this user session:
    deviceHasTouchID  = false
    deviceHasFaceID   = false
    deviceHasOpticID  = false
    isAppleSilicon    = false
  (probe then segfaults on _deviceClass; the first five answers are valid.)

Verdict: the icon is gated by MobileGestalt's capability answer, which is
derived from kernel/device state, plus an entitled XPC module. It is not a
user-space switch, a defaults key, or a loginwindow asset. Forcing it requires
injecting into coreauthd (SIP off) AND still leaves SEP-backed enrollment
unsatisfied. No user-space route exists.
